# 新突破！原生支持 Wayland 的 deepin wine 来了

前段时间儿子高考，我心底一直莫名心绪不宁。明明清楚自己没法替孩子分担什么，却还是控制不住地紧张焦虑。生活心绪虽有起伏，手头工作却丝毫不能松懈。过去几个月，我的主要工作是开发原生适配 Wayland 的 Wine 版本。

我曾在《从 X11 到 Wayland，迈出这一步为何如此艰难？》一文中解释过，从 X11 迁移至 Wayland，绝非单纯替换一套图形技术，可以说是一次桌面生态迭代。在 Linux 体系中，Wine 承担着从 Windows 平滑过渡到 Linux 的关键作用，因此桌面切换到 Wayland 的过程中，Wine 原生适配的意义格外重大。

如今 Ubuntu、Fedora 两大主流 Linux 发行版，均已默认采用 Wayland 桌面环境。但当前 Wine 稳定版本并未原生适配 Wayland，只能依靠 XWayland 兼容层间接运行。这种方案本质是在 Wayland 架构之上嵌套一套完整 X11 环境，不仅抬高了系统架构复杂度，还衍生出大量兼容问题。究其根源，X11 与 Wayland 底层设计思路截然不同，依靠兼容层根本无法完整复刻原生 X11 的运行逻辑。

其实 Wine 社区数年前就启动了 Wayland 适配工作，但推进速度一直比较慢。最大阻碍在于 Windows 图形编程逻辑与 Wayland 协议存在根本性冲突，大量 Win32 窗口、交互 API 很难在 Wayland 框架下落地实现。好在 Wayland 协议本身设计灵活，核心主干简洁精炼，各类拓展需求都能通过配套扩展协议补足。经过这么多年开发者的努力，如今已经标准化了许多扩展协议。

但扩展协议存在天然短板，不同 Wayland 合成器对各类扩展的支持程度参差不齐，有的完全未实现，即便支持，实际运行表现也存在差异。而 Wine 作为面向全 Linux 发行版的通用开源项目，仅能兼容标准化扩展协议，或者被绝大多数合成器实现了的扩展协议。同时，Wayland 官方社区也不允许为适配 Wine 的专属需求新增或修改协议。多重约束之下，原版 Wine 在 Wayland 环境中的运行体验始终差强人意。

Deepin 发行版在该领域具备独有的技术优势：我们基于上游 Wine 源码进行深度二次开发，打造专属 Deepin Wine，可与自研 Wayland 合成器 Treeland 深度适配、无缝联动。针对 Wine 运行时的各类特殊业务诉求，我们能够自研私有 Wayland 扩展协议。这类定制扩展难以纳入上游 Wayland 标准体系，配套的 Wine 适配补丁也无法合入上游主线，但并不妨碍 Treeland 与 Deepin Wine 实现深度协同优化。

下面借此机会，梳理汇报我们在 Wine 适配项目中落地的核心工作。

第一，攻克窗口精准定位难题。在 Windows 与传统 X11 架构中，应用可直接通过坐标、宽高参数自定义窗口显示区域。而 Wayland 在设计上做了完全相反的设定：窗口的摆放位置全权由合成器管控，应用自身无权指定坐标。这就带来明显的兼容问题：Windows 程序代码中预设的窗口居中逻辑，迁移到 Wayland 环境后会失效，窗口往往直接出现在屏幕左上角。若是多窗口类复杂业务软件，各窗口排布还会出现严重错乱。不只是 Wine，大量原生 Linux 桌面程序同样有自定义窗口位置的需求，但 Wayland 上游社区始终坚持现有设计，迟迟未推出标准化相关协议。为此我们基于 Treeland 自研私有扩展协议，彻底化解了窗口定位兼容痛点。

第二，Wayland 协议部分交互逻辑设计存在缺失，使用体验很不友好。例如 Surface 层面支持最大化、全屏、尺寸变更的状态通知，唯独缺少窗口最小化事件回调。窗口执行最小化操作后，应用无法收到对应的状态变更通知，Windows 程序也就无从知晓当前窗口已被收起……
